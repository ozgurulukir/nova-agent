# Nova Engineering Patterns & Reference Notes

Hard-won implementation knowledge for developing Nova, extracted from AGENTS.md so the system-prompt rules stay lean. This file is NOT ingested into the system prompt — read the relevant section on demand when working on a subsystem (TUI, MCP, Lua plugins, AI tool schema, type system, models.dev, config layering, reasoning, compaction, session resume).

## Architectural Layering & Invariants

### Subsystem Layering & Leaf Module Rules (`INV-LEAF-1`)

The codebase enforces strict hierarchical module layering:

1. **`lib/` (Leaf Utility Layer):**
   - Contains pure leaf modules (`bounded_queue.zig`, `counting_allocator.zig`, `logger.zig`, `platform.zig`, `terminal_markdown.zig`, `websocket.zig`).
   - **`INV-LEAF-1` Invariant:** Modules in `lib/` must **NEVER** import anything from `src/` (0 reverse dependencies).
   - Must be independently compilable and testable as standalone packages.
2. **`src/tools/` & `src/ai/` (Adapters & Execution Primitives):**
   - Protocol clients (`responses_core.zig`, `openai_compatible.zig`), SSE parsers (`stream_part.zig`, `responses_events.zig`), wire serializers (`responses_request.zig`), and tool safety/validation (`executor_safety.zig`, `executor_validation.zig`).
   - Zero presentation/TUI dependencies.
3. **`src/agent/` (Cognitive & Lifecycle Orchestration):**
   - Turn execution loops, conversation tree management, context compaction, and subagent session coordination.
4. **`src/tui/` (Presentation & View Layer):**
   - User interface, terminal rendering via libvaxis/vxfw, and keyboard/mouse event dispatch.
   - **`INV-WIDGET-1` Invariant:** Leaf widgets under `src/tui/widgets/` must never hold pointers to `App`; they receive pure view models or scalar state (`has_model_configured: bool`).

## Patterns

TUI built with libvaxis vxfw (source in zig-pkg). Prefer framework primitives.

**vxfw gotcha:** `TextField.widget()` is _mutating_ — it takes `*Self`, not `*const Self`. Accessors returning `*TextField` must be declared on `*App`, not `*const App`, or the call site fails to type-check.

**Zig 0.16 field rule:** `pub` cannot precede a field declaration — only functions/variables. Cross-module field access goes through `pub fn` accessors (`getX()` form, never `X()`, because of the field-vs-method name collision).

### TUI module split

`src/tui.zig` holds `App` lifecycle and `RootWidget`; `src/tui/` is split by concern. See `README.md` Architecture for the current module list.

### App state grouping pattern

`App` struct fields are grouped into focused sub-structs defined in `src/tui/app_state.zig`: `InputState` (text fields), `PickerStates` (per-picker state), `NavState` (cursors + quit state machine + session action + resume group-by), `ListWidgets` (scrollable list views), `ProviderState` (API keys + registry + connectivity), `InputBuffers` (inline edit buffers), `AtSearchState` (`@`-mention search), `BackgroundModalState` (Ctrl+O modal), `MetricsState` (spinner + diff cache). Each sub-struct owns one concern; accessors on `*App` expose inner fields. When adding new App state, prefer extending an existing sub-struct or adding a new one rather than growing the flat struct.

### Domain extraction pattern

Isolated domain clusters (lane lifecycle, diff lifecycle, session switching, at-search, transcript navigation, permission, event callbacks, queue, settings lifecycle, clipboard helper, search lifecycle) live under `src/tui/` as free-function modules. Each module imports `const tui = @import("../tui.zig")` and defines `pub fn` taking `*App` as the first parameter. The original App method stays as a 1-line delegate (Strangler Fig) so tests in `src/tui/tests.zig` resolve via the struct. When a private App method is needed, promote it to `pub` — not `pub const` (that is for module-level re-exports of nested types). The TUI test blocks live in `src/tui/tests.zig`, wired into the test run by `_ = @import("tui/tests.zig")` in `root.zig`'s `test` block — a lazy `pub const tests` on `tui.zig` does NOT compile them (the file is never analyzed), so the reference must take the file's address.

The same extraction shape applies below the TUI: pure shared leaves get their own root/`src/ai` module with the old site re-exporting as a facade — `src/paths.zig` (path comparison, re-exported by `tui/lanes.zig`), `src/ai/model_compat.zig` (model/dialect quirks, re-exported by `openai_compatible.zig`), and `src/ai/openai_request.zig` (chat-completions payload serialization) alongside the existing `responses_request.zig`/`responses_events.zig`. Every new module needs an `_ = @import(...)` in `root.zig`'s `test` block — that is the load-bearing half that makes its inline tests run (a lazily-referenced file is never analyzed); a `pub const` in the decl list additionally exposes it through the module registry (`paths.zig` has both; the `ai/*` siblings are exposed via `ai.zig`'s re-exports instead).

### Widget extraction pattern

Isolated widgets live under `src/tui/widgets/`. A new widget file declares the outer border widget as:

```zig
pub const NameWidget = struct { app: *App, pub fn widget(...) vxfw.Widget { ... } }
```

with a private `Inner` struct built inside `draw()` from a `vxfw.DrawContext`. The file imports `const tui = @import("../../tui.zig");`, `const tui_style = @import("../style.zig");`, `const panel = @import("panel.zig");` and re-aliases `const App = tui.App;`. Nested types from other modules are re-exported through `pub const` in `tui.zig` so widget files reach them as `tui.<module>.<Type>`.

INV-WIDGET-1 scalarization contract (established by `transcript.zig`/`loading.zig`): a leaf widget that only draws values takes scalar fields instead of `app: *App` — the per-frame construction site (`root_layout.drawRoot`, `lane_column.drawLaneColumn`) computes them from `app` right before building the widget literal, so there is no staleness window. State the widget cannot own flows through pointers: `TranscriptWidget.blackhole_visible: *bool` writes back into `App.metrics` so the intro-animation tick can stop. `MessageListBuilder` (same file) is the isolated-view-model form for list building.

### Timeline overlay flatten pattern (`/timeline`)

`src/tui/widgets/tree_selector.zig` owns the full session tree (`TreeState.nodes`, rebuilt on `load`) and derives the visible layout on each `reflatten` from the filter mode, fold set, and search. Invariants worth preserving: legacy `checkpoint`-kind entries never render as rows (their descendants attach to the nearest visible ancestor); the conversation leaf is always visible (`is_leaf or kindPasses`, so the current row survives any filter); a snapshot-bearing entry hidden by filter/search migrates its ✦ to the nearest visible ancestor, with the deepest snapshot in a collapsed segment winning (`last-write` into `snap_id`); `reflattenKeepingSelection` restores selection by id and clamps to the last row when the selection is filtered out. `load` resolves the leaf to the nearest real message (a checkpoint may be the leaf) so a row — not nothing — is selected on open.

### Per-mode command routing

`src/tui/command_router.zig` holds one struct per `App.Mode` variant, each owning a `handle` method migrated from `App`. The dispatcher is a free function delegating to the right struct. Add new per-mode logic here — don't reintroduce private methods on `App` for key handling.

### Viewport scrolling pattern

Standardize overlay list viewports using `panel.ViewportWindow.compute(selection, total_count, surface.size.height)` in `src/tui/widgets/panel.zig`. Use `viewport.screenRow(i)` for row rendering calculations.

### Provider polymorphism pattern

Unify static builtin `config_mod.Provider`, dynamic `modelsdev.Provider`, and user-defined `config_mod.ProviderConfig` handles using `ProviderHandle = union(enum) { builtin, dynamic, config }` in `src/tui/widgets/provider_picker.zig`. All three share the same accessor surface (`id()`, `displayName()`, `description()`, `defaultBaseUrl()`, `requiresApiKey()`, `catalogueIndex()`). The `/connect` picker builds a single merged list via `buildMergedProviderList` in `src/tui/provider_model.zig`: builtin catalogue → models.dev registry (overrides builtins with same id) → config providers (overrides everything with same name, **except** entries already covered by the models.dev registry — a `reg.lookup(cp.name)` guard prevents the persisted `ProviderConfig` entry from shadowing the `.dynamic` handle and converting the provider to a "custom" entry in the picker).

### Provider key masking pattern

The `/connect` setup form (`drawForm` in `src/tui/widgets/provider_picker.zig`) masks the API key with `maskSecret` (one `•` per grapheme) so a secret is never rendered in plaintext on screen. The mask is lifted **only while the user is actively editing** the field: `State.key_dirty` flips to `true` on the first real edit (text/codepoint/backspace in `ProviderPicker.handle`, `command_router.zig`; **and** on paste in `pasteToFocusedInput`, `clipboard_helper.zig`, which bypasses the router) and the live input renders in plaintext so a pasted key is verifiable. A pre-filled existing key (form opened to edit) stays masked until the first keystroke. `key_dirty` is reset on every form open (`State.reset()` and `openProviderEntryForm`), so the mask always returns when the form closes — there is no persistent "reveal" toggle. Do not re-mask while typing: that would defeat paste verification, the whole point of the plaintext-while-editing behavior.

### System clipboard pattern

`src/clipboard.zig` handles OS clipboard reading/writing via terminal OSC 52 sequences (`\x1b]52;c;<base64>\x07`) with OS-native execution fallback (`wl-copy`/`xclip`/`pbcopy`/`powershell` via `bash.zig`). `clipboard_helper.zig` routes clipboard data dynamically to focused input fields and transcript message blocks.

### Settings lifecycle pattern

`src/tui/settings_lifecycle.zig` manages pending tabbed form edits, syncs values to `app.cached_config` in real-time, and serializes user settings on `Ctrl+S`. `saveSettings` writes only settings-managed fields (`use_responses_endpoint`, `system_prompt`, `bash_classifier_url`) — never provider/model. If a project config exists (`.nova/config.json`), settings are written to both global and project configs; otherwise global only. This prevents project-level provider/model overrides from leaking into global config. The General tab holds a single toggle (`use_responses_endpoint`); reasoning is not a settings-panel concern — it is controlled per-model via the model picker and persisted session-scoped (see **Reasoning effort lifecycle pattern**).

### MCP Server & Tool Discovery pattern

`src/mcp/manager.zig` merges `mcp_servers` configuration across global/project layers (supporting `mcp_servers`, `mcpServers`, and `mcp` JSON aliases) into `McpClient` objects. Transports are `union(enum) { stdio, sse }`; the `{env:VAR}` security model, async-connect lifecycle (`ConnectJob`/`drainConnects`/`installConnectResult`), timeouts, tool injection, and crash isolation are documented in [MCP](MCP.md#3-connection-lifecycle). The `McpMode.handle` routing in `command_router.zig` maps `Up`/`Down`/`j`/`k` to navigation, `Space`/`Enter` to toggle, `Ctrl+R`/`r` to re-sync, `d` to disconnect, `a` to add a remote server by URL (a `State.adding` sub-state fed by the `input_buffers.mcp_url` buffer; **runtime-only** — appended to `cached_config.mcp_servers`, never persisted to config.json; URL-only, no headers), and `Esc`/`q` to close.

### Lua Plugin System pattern

`src/lua/` implements a full Lua 5.4 plugin SDK. `PluginManager` (manager.zig) discovers plugins from `~/.config/nova/plugins/` (global) and `.nova/plugins/` (project), loads manifests (`plugin.lua`), and creates sandboxed Lua states. The `App` struct holds `plugin_manager: lua_mod.PluginManager` and `tool_registry: *tools.ToolRegistry`; the `/plugins` TUI overlay lists loaded plugins with active/inactive status. The development guide, `nova.*` bridge-function reference, and examples live in [Plugins](plugins/README.md) / [API reference](plugins/api-reference.md).

### Plugin event wiring pattern

`nova.on(event, callback)` subscribes to lifecycle events by storing callback refs in each plugin's `"nova_events"` Lua registry table. Events are emitted by `Agent.ExecutorBridge` at tool-call boundaries — `onStarted`/`onFinished` (agent.zig) call `plugin_manager.emitEvent(.{ .tool_call_started = ... })` / `.tool_call_finished`. `PluginManager.emitEvent` (manager.zig) iterates every active plugin and drains its `"nova_events"` sub-table for the event name, pcalling each stored callback ref with the payload pushed as a Lua table via `events.pushEventData`. This multi-state dispatch (one Lua state per plugin) replaced the old single-state `EventBus` struct, which was dead code. Event types: `turn_started`, `turn_ended`, `tool_call_started` (`{name, call_id}`), `tool_call_finished` (`{name, call_id, success}`), `response_received`, `plugin_loaded`, `plugin_unloaded`. Reentrancy is safe because the agent worker is single-threaded and emits at tool-call boundaries (after the plugin's own handler has returned).

### Plugin glob matcher pattern

`nova.find_files(root, pattern, opts?)` walks `root` recursively and matches each file's relative path against a glob pattern via `matchGlob` (plugin_api.zig). Supports `**` (spans directories), `*` (within a segment, does not cross `/`), `?` (one char). The matcher is segment-aware: `src/*.ts` does not match `src/nested/a.ts` (only `*` not `**`), but `**/*.ts` matches at any depth. max_results cap (200, default 100); gitignore is NOT honored (use `run_bash` with `rg --files` if needed). `matchGlob` is public for unit testing; the 8-test suite covers empty/literal/star/double-star/question-mark cases.

### Skill subsystem pattern

`src/skill.zig` owns project/global skill discovery, system-prompt publication, and `$name` invocation expansion. `loadProject(gpa, io, home_dir, cwd)` scans two roots — `<home>/.agents/skills` (global, optional) then `<cwd>/.agents/skills` (project) — each via `loadFromDir` (depth-capped at `max_skill_depth = 8`). A project skill with the same name displaces its global counterpart (`shadowDuplicates`, mirroring `plugin_prompt.replaceOrAppend`); two same-name project (or two global) skills both load, first-wins for `find`, and are surfaced by `warnDuplicateNames`.

**Name validation:** every loaded skill must have a valid, invocable name — no whitespace, `$`, empty, or >64 bytes (`isValidSkillName`) — or it is skipped with a warning (`error.InvalidSkillName`). Loose root `.md` files fall back to their file stem for a name; `SKILL.md` files fall back to their directory name. **Injection budget:** `promptPrefix` enforces a cumulative `max_total_invocation_bytes` (256KB) across all invoked skills; `appendSkillBlock` checks the budget against `stat.size` *before* allocating and returns `error.SkillBudgetExhausted`. **Graceful degradation:** `promptPrefix` catches every non-OOM `appendSkillBlock` error and writes `[skill '<name>' could not be loaded: <err>]` inline instead of failing the turn. **Case-insensitivity:** `find`/`collectInvocations` match skill names case-insensitively (`std.ascii.eqlIgnoreCase`), aligning invocation with the popup (`filterNames`). **Frontmatter parser:** `frontmatterValue` skips indented (nested) lines so nested YAML keys can't shadow top-level ones; block-scalar indicators (`|`, `>`, `|-`, `>-`, `|+`, `>+`) are rejected (`error.BlockScalarUnsupported`). **XML escaping:** `appendSkillBlock` (user-message blocks) routes attribute values through `writeXmlEscaped` (SSOT); `formatForPrompt` (system-prompt skill list) renders markdown bullets (`- **name** — description`) instructing the model to load skills on demand via the builtin `skill` tool (`src/tools/skill.zig`), while users can invoke upfront with `$name`. **Resume markers:** `collectInjectedSkillNames` parses `<skill name="…">` markers from user messages so `rebuildTranscriptFromAgent` (transcript_lifecycle.zig) restores `[SKILL]` rows on resume. **Palette visibility:** the `/skills` command (`formatSkillsList`) lists every loaded skill with name, description, and path.

### Plugin prompt injection pattern (`prompt.md`)

Each plugin directory MAY ship an optional `prompt.md` describing how the model should use that plugin's tools. `src/plugin_prompt.zig` scans `<home>/.config/nova/plugins/*/prompt.md` and `<cwd>/.nova/plugins/*/prompt.md` (project overrides global on directory-name collision) and strips YAML frontmatter via `skill_mod.stripFrontmatter` (reused from `src/skill.zig`). The markdown bodies are injected into the system prompt as a `<plugin_prompts>` block by `plugin_prompt.formatForPrompt`, appended in `context/assembly.zig` `assembleSystemPrompt` step 5 — parallel to the `SKILL.md` → `<available_skills>` flow. This is a **pure text scan, no Lua state** — it runs early in `runtime.zig` `initSession` (alongside skill loading), before `PluginManager`/`App.initRuntime` create any Lua states. Because `assembleSystemPrompt` bakes the prompt once, plugin prompts reach the model via `system_prompt` only; a freshly-added `prompt.md` takes effect on the next session/lane. The scan mirrors `PluginManager`'s directory conventions (same `global_dir`/`project_dir` roots) but is intentionally decoupled — a plugin with `prompt.md` but no `plugin.lua` still contributes prompt text, and a plugin with `plugin.lua` but no `prompt.md` contributes none. Plugins whose body is empty after frontmatter stripping are skipped (uniform `error.FileNotFound` path).

### Plugin tool dispatch via ToolRegistry pattern

Plugin tools registered through `nova.register_tool` are materialized as `tools.Tool` records in `src/lua/registry_bridge.zig` and inserted into the `ToolRegistry` via `provider_model.registerPluginTools(self)`. Each `Tool` carries a `*PluginToolKey` in its `userdata` field; the shared `runPluginTool`/`displayPluginTool` dispatchers decode the key and route the call to the correct `(plugin_name, tool_name)` handler through `PluginManager.callTool`. The `*const fn` signature on `Tool.run`/`display` is preserved by passing `userdata: *anyopaque` as the last argument — the dispatcher `@ptrCast`s back to a `*PluginToolKey`. `Tool.userdata_free: ?*const fn (gpa, *anyopaque) void` lets the registry release each tool's heap-allocated state. The App's `initRuntime` calls `registerPluginTools` right after `plugin_manager.loadAll()`, which puts the tools in the registry. Plugin tools still use the `lua__<plugin>__<tool>` naming convention so the model can disambiguate them. `executor.runOne` dispatches every non-`mcp__` call through `tool_registry.all(...)` + `tools.runWith` — no `lua__` prefix branch.

**Tool visibility to the model:** a client only advertises tools that are in its serialized `tools_json`. The client is built at `attach` time, but the registry (which carries plugin tools) is set on the agent afterwards — so the freshly-attached client would otherwise keep its builtin-only `tools_json` and never learn about `lua__<plugin>__*` / `mcp__<server>__*` entries. `runtime.replaceClient` guards its `updateMcpTools` rebuild on `tool_registry != null`: during `initSession` (applyFromConfig — every `/new`, `/resume`, lane spawn) the App hasn't wired the registry yet, so rebuilding with a null registry and the empty builtin override would serialize `"[]"` and wipe the builtin tool definitions (shell/lane/background) `init` just built. `createRuntime` (session_switcher.zig) closes the gap for freshly-created runtimes: after wiring `agent.tool_registry` / `mcp_manager` / `plugin_manager`, it calls `provider_model.injectToolsInto` to push the merged tool list (builtin + plugin + MCP) into the new client in one shot. The `OwnedClient.updateMcpTools` union helper dispatches to all three concrete clients (`codex_responses`/`openai_compatible`/`openai_responses`). `injectAllTools`/`refreshMcpTools` (provider_model.zig) push MCP+plugin schemas again on `/mcp` and `/plugins` open, toggle, and reconnect. Without the `createRuntime` push, the new session's main client ran tool-less until an unrelated MCP event — the user-visible symptom was `openai_compatible: sending request with NO tools (tools_json is empty)` on every turn.

### Plugin tool parameter parsing

`callToolHandler()` in `plugin_api.zig` parses the JSON arguments string into a Lua table before calling the handler, using `pushJsonToLua()` / `pushJsonValue()` which recursively convert `std.json.Value` to Lua values (objects → tables, arrays → 1-indexed tables, strings/numbers/booleans → corresponding Lua types). Plugin handlers receive `params` as a proper Lua table — `params.depth`, `params.pattern`, etc. work directly without manual JSON parsing. `pushJsonValue` is `pub` (not private) because `nova.json_decode` reuses the same Zig-JSON→Lua conversion — do not re-implement it.

### Two-store lazy-load plugin pattern (todo plugin)

When a plugin manages both a compact list (frequently read, shown on every call) and bulky detail records (rarely needed, large), keep them in **separate stores** so the list view never pulls the detail into context. The todo plugin is the reference: `.nova/todos.txt` holds the todo.txt task list (one line per task, editable in any editor, spec-portable), while `.nova/todos/plans.json` holds detailed plans (`{summary, steps[], notes}`) keyed by a stable `id:N` tag. `todo_list` reads only `todos.txt` and shows a `[plan:N steps]` *marker* (count, not body); the full plan is fetched on demand via `todo_get_plan(id)`. This is the context-hygiene boundary: a 16-task list costs one short line each, and a multi-hundred-token plan enters context only when the model is actively working on that one task. Three implementation rules: (1) the list store stays plain-text/editable (don't bury it in JSON); (2) the detail store uses `nova.json_encode(plans, {pretty=true})` so it is human-readable and round-trips cleanly via `nova.json_decode`; (3) the key linking them is a stable identifier persisted in the list store itself (the `id:N` todo.txt key:value tag — promoted to `t.id` in `parse_line`), NOT the array index, because `table.remove` shifts indices on delete while ids stay valid across edits. `load_todos()` reads fresh from disk on every call (no `_G.todos` cache across turns) so external edits to `todos.txt` are always reflected — the old cache-once behavior masked out-of-band edits. `load_plans()` returns `{}` on missing-or-corrupt so a bad sidecar never blocks the task list.

### Plugin bridge function pattern

All `nova.*` bridge functions are C-callable `lua_CFunction` registered in the `nova` global table by `registerPluginApi()` in `sandbox.zig`. Each function receives `?*c.lua_State`, extracts arguments via `bridge.pullValue()`, performs the operation through Nova's safe Zig APIs (path validation via `sanitizePath()`, shell execution via `pwsh_exec` / `bash_exec`), and returns results as Lua values. The `std.Io` instance is stored in the Lua registry (`nova_io`) for filesystem access. Currently 29 bridge functions across 6 categories: Filesystem (10: `read_file`, `write_file`, `edit_file`, `search_files`, `find_files`, `list_dir`, `file_info`, `mkdir`, `copy_path`, `delete_path`), Shell & Env (5: `run_shell`, `run_bash`, `get_env`, `get_cwd`, `get_project_root`), Git (6: `git_status`, `git_diff`, `git_log`, `git_branch`, `git_add`, `git_commit`), Plugin System (4: `require`, `register_tool`, `on`, `think`), JSON (2: `json_decode`, `json_encode`), plus `shell_quote`. The registration table in `sandbox.zig` is the source of truth when adding more. Relative module loading is provided via `nova.require(mod_path)` (scoped strictly to plugin directory and cached in `nova_loaded_modules`). The JSON bridges — `nova.json_decode(str)` and `nova.json_encode(value, opts?)` — let plugins parse and emit structured data without hand-rolling a parser or shelling out to `jq`. `json_decode` reuses `pushJsonValue` (Zig `std.json.Value` → Lua); `json_encode` traverses the Lua value with `lua_next`, inferring array vs object from key shape (`lua_rawlen == lua_next` entry count → array `[...]`, else object `{...}`), and writes to an allocating writer with optional `{pretty=true}` for indent_2 output. Empty tables serialize as `[]` (the common plugin convention for an empty list). Functions/userdata/threads (no JSON form) emit `null` rather than failing the whole encode. The encode helpers (`writeLuaValueJson`/`writeTableJson`/`writeTableAsArray`/`writeTableAsObject`) share an explicit `JsonWriteError = std.Io.Writer.Error` to break the inferred-error-set dependency loop created by their mutual recursion.

- **Plugin cwd resolution:** All plugin cwd resolution goes through
  `bridge.resolvePluginCwd` (`src/lua/bridge.zig`), which reads
  `plugin_cwd_slot` (lane worktree OR `/resume` session cwd) or falls back to
  the process cwd. Never call `std.process.currentPathAlloc` directly in a
  bridge.
- **Event callback cwd window:** Plugin event callbacks (`on_started`/`on_finished`)
  run inside `runAll`'s `plugin_cwd_slot` window, set around the whole batch
  and refreshed by `rerootFromRequester` on mid-batch lane ops. This ensures
  fs/shell/git bridges called from event handlers see the correct effective cwd.

### Tool schema strict-mode pattern

OpenAI strict structured-outputs mode (`"strict":true`, `additionalProperties:false`, `required:[all properties]` with optionals made nullable) is **opt-in via `ai.Config.strict` (default `false`)** — it only works against the OpenAI API and silently breaks function-calling on gateways (OpenRouter/Ollama/vLLM/Together), which causes the model to emit tool calls as plain text (`<function=...><parameter=...>`) instead of `tool_calls` deltas. Tool-definition serialization lives in a **single** place: `src/ai/tool_schema.zig` — `buildAllToolsJson`/`writeToolDefinition`/`writeParameters` thread `strict: bool` end-to-end and take an `Envelope{completions,responses}` that encodes the only wire-format difference (Chat Completions wraps each definition in a `"function"` object; Responses emits it flat). `openai_compatible.zig` calls it with `.completions`, `responses_core.zig` with `.responses`. The `Client.strict` field captures strict at `init` so `updateMcpTools` rebuilds `tools_json` consistently. The inline golden test (`tool_schema golden: byte-identical output…`) locks the produced bytes for both envelopes × strict on/off — the closure-brace count per envelope is easy to get wrong, so the golden is the regression guard. When `strict` is off: the `"strict"` key is omitted (the leading comma before `"parameters"` is still written so the JSON stays valid), and `required` lists only genuinely-required properties. The setting flows `config.strict_outputs: ?bool` → `AgentRuntime.strict_outputs` (set at session init and re-synced from `cached_config` at every connect) → `.strict = self.strict_outputs` on the three `client.init` call sites (codex/openai_compatible/openai_responses) in `runtime.zig`. Enable it with `"strictOutputs": true` in config.json or `NOVA_STRICT_OUTPUTS=1`. There is **no provider auto-detection** — defaulting strict off keeps tool-calling working everywhere; OpenAI direct users opt in explicitly.

**Persistence:** `strict_outputs` is a global (API-level) setting, not model-scoped, so it is **not** carried on `ModelSelection`/`BuiltinSelection`/`CustomSelection` (unlike `use_responses_endpoint`/`enable_thinking`/`system_prompt`/`bash_classifier_url`). `parseObject` therefore does **not** clear `out.strict_outputs` when building `model_selection` (the four model-scoped settings are cleared), leaving it on `config` for `serialize` to read. `serialize`'s `model_selection` branch (the production path) must read `config.strict_outputs` directly and write `strictOutputs` — the earlier code wrote it only in the legacy branch (`model_selection == null`, i.e. tests), so the setting vanished on the next save in normal operation and reset to `false` on restart.

### Background jobs & agent tool pattern

Design spec: `_plan/plan-background-jobs-agent-tooling-2026-08-17.md`. Nova manages asynchronous, long-running processes launched with `run_in_background: true` via `BackgroundManager` (`src/background.zig`). The AI model queries and controls these jobs through the builtin `background` tool (`src/tools/background.zig`, with operations `list`, `status`, `cancel`, `tail`). Access to `BackgroundManager` is established through a scoped thread-local context slot (`BackgroundSlot`) bound in `ExecutorService.produceOutput` and cleanly restored via `defer`. Bounded reverse file reading (`readLogTailBounded`) scans at most the trailing 64 KB, skips leading UTF-8 continuation bytes, and tolerates missing or non-existent files gracefully across Windows and POSIX.

### Tool argument validation pattern

`ExecutorService.runOne` validates every tool call's `arguments` JSON against the tool's `tools_common.Schema` **before dispatch**, in a single choke point shared by all three channels (builtin / plugin / MCP): `resolveSchema` finds the schema (MCP via `mcp__<server>__<tool>` parse + `full_name` match against connected clients; builtin/plugin via one registry `all()` lookup), and `src/tools/schema.zig`'s pure `validateArgs` produces a `ValidationResult` whose violations become a structured model-facing error (`Invalid arguments for tool 'bash': \`command\` is required`) instead of letting the tool run on garbage. `validateArgs` converts every non-OOM failure (parse error, wrong type, missing field, null-when-not-nullable, enum miss) into a violation internally, so the only error it propagates is `OutOfMemory` — `runOne` does `catch return error.OutOfMemory`. Type rules: JSON integers satisfy both `integer` and `number`; floats only `number`; quoted `"42"` is neither; `std.json.Value.number_string` (an i64-overflowing JSON number token) counts as a number. Unknown tools (no schema) skip validation. v1 does **not** check `additionalProperties` or nested object/array element schemas. `runValidationError` is separate from `runFailure` (execution errors) and leaves it untouched; tests cover all three channels plus a positive control.

### Retry/backoff pattern (`openai_compatible` only)

`ai.Config` carries `max_retries` (default `2`) and `retry_base_delay_ms` (default `500`) — `max_retries = 0` is the legacy single-attempt kill-switch. `Client.prompt` serializes the payload **once** per cache mode (via `openai_request.writeRequestPayload`), then loops `sendOnce`; only head-phase failures are retried while attempts remain: 429 (`error.HttpRateLimited`), 5xx (`error.HttpServerError`), and connection drops classified by `headPhaseFailure` as `error.ConnectionFailed` (socket errors plus `error.HttpConnectionClosing` — std.http's report for reusing an idle keep-alive connection the server already closed). Every other 4xx is permanent (schema/auth/model errors don't self-heal) and stream-mid errors never surface as these codes, so partial deltas are never double-delivered. `Retry-After` (integer seconds, case-insensitive, parsed from `http_response.head.bytes` *before* the body reader is initialized — head pointers die at body start) takes precedence over exponential backoff `base * 2^attempt`, which is capped at 8000 ms. The mock-server tests (`MockRetryServer` over `std.Io.net` ephemeral-port listen/accept + `std.http.Server`) exercise 503→200, 429→200, permanent-4xx no-retry, retry exhaustion, and the kill-switch — the retry decision, delay computation, and header parsing are also covered by pure unit tests.

**C2 cache-downgrade retry (added 2026-08-06):** a 400 whose error body mentions "cache" (`errorDetailMentionsCache`, case-insensitive) earns exactly ONE cache-stripped re-send — the payload is rebuilt with `disable_prompt_cache = true` (drops OpenRouter `cache_control` + `session_id`, OpenAI `prompt_cache_key`) and the FULL 429/5xx retry budget is replayed on the stripped payload. This is a *separate* failure mode from 429/5xx, so it's decoupled from the `attempt` counter via a `downgrade_done` one-shot gate and an outer `while (true)` loop that runs at most twice (original + stripped). Zig's `while … : (step) { continue }` runs the step expr, so riding the counter would burn a user-facing retry slot. The downgrade is gated on `!disable_cache` (no fields to strip if the user already disabled caching) and on `err == error.HttpClientError` (only a 400 — not 429/5xx). Conservative "cache" substring match; a false positive costs one extra request and then fails normally.

### Outbound provider headers pattern (`provider_headers.zig`)

Single source of truth for headers on an outbound AI request: the INV-RESP-1 sibling leaf `src/ai/provider_headers.zig`, imported by BOTH wire transports (chat-completions `sendOnce`, Responses `extraHeaders`) and the `/v1/models` probe — never through each other. It owns the spec type (`Header{name, HeaderValue}` where `HeaderValue = literal | session_id | account_id`, aliased back into `ResponsesConfig` so the codex profile table compiles unchanged), the merge policy (`build`), and the zero-alloc per-request materializer (`HeaderSet` over a `[max_outbound_headers]` stack buffer, which every send site sizes; `8 profile + 8 user + 3 auto`). Two header classes flow through it: **auto** headers a provider requires/merits — the OpenCode Zen routing pair `x-opencode-session` (value = the 32-hex session id, resolved per request from the client-owned `config.session_id`) + `x-opencode-client: nova`, both mandatory on `opencode.ai/zen*` URLs since 2026-09-05, and the OpenRouter attribution `X-Title: Nova` (migrated from the chat client's deleted `app_title`/`app_referer` fields) — and **user** headers from `providers.<name>.headers` (MCP-style `{env:VAR}` raw-on-disk, expanded at attach time by `config/provider.zig::expandProviderHeaders`). Precedence is resolved in exactly one place, inside `build`: a user header whose name matches an auto header (ASCII case-insensitive) replaces it; non-colliding user headers follow in config order. Zen routing headers are transport identity, NOT cache hints: `build` never sees `disable_prompt_cache`, so the flag cannot suppress them. Data flow: `parseProviderHeaders` (validation: name must be token-safe single-line, value non-empty single-line; reserved transport names — `authorization`, `content-type`, `host`, `content-length`, `transfer-encoding`, `connection` — rejected with a warn; capped at 8) → `ProviderConfig.headers` → runtime `buildProviderHeaders` (`expandProviderHeaders` + `build`, resolved once per attach — headers frozen until the next attach, mirroring MCP connect-time expansion) → `ai.Config.headers` (BORROWED; both clients deep-dupe via `provider_headers.cloneHeaders` into `provider_headers_owned`, freed in `deinit`) → `HeaderSet.append` per request. The Responses client appends its static protocol profile (codex handshake set) BEFORE the provider set, so profile headers win name collisions (`accept`/`OpenAI-Beta` are functional, not styling). The chat compaction/naming clients now carry `session_id` too (the old gap left the zen session header empty on summarizer/branch-naming traffic). The models probe builds its own specs from the URL (`listModels(..., Options{session_id, user_headers})` — job-owned session-id dupe in `model_loader.Job`, because the App may switch sessions while the background probe runs). Serialization writes headers back RAW (placeholders preserved) — a settings save never leaks a resolved secret.

### Zero-copy historical pruning pattern

`Agent.run` sends `client.prompt` a `[]const ai.MessageView` (defined in `ai.zig`) instead of a deep copy of the history: `pruneHistoricalToolResultsViews` (context/assembly.zig) BORROWS every unchanged message straight from the ContextManager (`.borrowed: *const ChatMessage` — base64 images are never re-duped per turn) and only historical tool messages older than the keep-recent cutoff become `.owned` pruned copies. `freePrunedViews` frees only `.owned`; borrowed views alias live manager memory and are valid for the duration of the synchronous `prompt` call because the manager appends only after it returns (`takeAssistantMessage`/`takeToolResults`). The pointer-identity test asserts an image's `data_base64.ptr` is identical to the source — the proof that no copy happened. All three clients (`LanguageModel.prompt` union) and both payload writers consume views; do not reintroduce whole-history cloning. `cloneContentBlock` remains only as the block-copy helper inside `pruneSingleToolMessage`. The pruning budget is configurable, not hardcoded: `Agent.run` passes `compaction_settings.keep_recent_tool_turns` and `.historical_tool_cap_bytes` (`context.compaction.keepRecentToolTurns` / `historicalToolCapBytes`), whose defaults mirror the `assembly.zig` constants. A long agentic turn (50+ tool calls, e.g. the multi-phase `tci-bfg` skill) shreds any result older than the keep-recent window to 1 KB, which small/flash models read as "output keeps getting compacted" — raise the cap/turns in config when a turn needs earlier results in full.

**Head+tail sandwich truncation (SSOT: `common.elideMiddle`).** Historical pruning (`pruneSingleToolMessage` → `common.pruneToolText`) and compaction's summarizer render (`cappedToolResult`) both truncate an oversized tool result as a head+tail sandwich — first half of the budget + last half, joined by `common.elideMiddle` with a `[... N of M bytes elided to save context ...]` marker — instead of head-only. Head-only truncation dropped the load-bearing conclusion (errors, test results, `rg` hits, `git status`) that lives at the tail, forcing the model to re-run commands to rediscover it. The bash spill `Full output:` footer sits at the very end and survives naturally inside the tail. `at_mention` file ingestion uses the same `elideMiddle` SSOT to read a mention's REAL head+tail (first half + last half of the 64 KB budget) so an oversized plan keeps its conclusion, with a `[file truncated: N bytes — re-read with read_file if you need the rest]` notice. Do not reintroduce head-only truncation at any of these sites.

### View reuse across run-loop iterations — analysis only (TD-13, deferred)

`Agent.run` rebuilds the views at the top of every iteration (`src/agent.zig:457-463`), up to 100 iterations/turn, re-allocating and re-truncating every historical tool message over the cap each time. Bounded but wasteful (~1 KB copy × historical-tool-messages × iterations). The naive cache (reuse views when `messages.len` unchanged) is **unsafe**: `MessageView.borrowed` points into the ContextManager's ArrayList backing, which `appendPersisted` may reallocate — dangling every borrow even when the length later matches. Per-index pruned copies ARE stable (pruning of message *i* depends only on `messages[i]` and the cap), so a v2 design caches only the **owned** pruned copies keyed by index, invalidated on `reloadFromSession` / branch switch / compaction swap, with borrows re-resolved against the live items slice each iteration. Do not implement the naive cache; measure first, then build the owned-copy cache with the invalidation story.

### Type System Discipline pattern

Use `union(enum)` instead of flat structs with optional fields whenever a value can be in one of several mutually-exclusive states. This makes illegal combinations unrepresentable at compile time. Current types following this pattern:

- `ai.ChatMessage` — `union(enum) { system, user, assistant, tool }`. The `tool` variant carries non-optional `call_id`; other variants cannot. `role()` and `text()` are cross-variant accessors.
- `transcript.Message` — `union(enum)` with 10 variants (`user`/`agent`/`skill`/`logo`/`thinking`/`status`/`notice`/`success`/`info`/`tool`). `Basic` and `ToolView` payload structs group fields by category. `kind()` bridges the loose `MessageKind` enum; `mirror()` is test-only flat view.
- `tools.Output.display` — `Display` union with `none`/`text`/`diff` variants, replacing the old `?[]u8 + DisplayKind` pair that allowed `null` with `.diff`.
- `config.McpServerConfig.transport` — `union(enum) { stdio, sse }`. A server is either stdio (command+args) or sse (url), never both or neither.
- `mcp.McpClient` — `transport: union(enum) { stdio, sse }` (static config) + `lifecycle: union(enum) { disabled, stdio, sse, failed }` (runtime state). `status()` maps lifecycle to the legacy `ServerStatus` enum.
- `config.Config.model_selection: ?ModelSelection` — typed view replacing 9 loose optional fields. `ModelSelection` is `union(enum) { builtin, custom }`: builtin carries `provider: Provider` + `provider_name`; custom carries `provider_name`, `base_url`, `api_key`. Optional settings (`use_responses_endpoint`, `system_prompt`, `bash_classifier_url`) live on both variants. Callers use accessors (`provider()`, `providerName()`, `model()`, `baseUrl()`, `apiKey()`, `useResponsesEndpoint()`, `systemPrompt()`, `bashClassifierUrl()`) so builtin/custom differences are hidden. The old `enableThinking`/`enable_thinking` config key is accepted-but-discarded at parse (reasoning is per-model via `providers.<name>.models.<id>.reasoningEffort`); it is not a field on `Config` or the selections anymore. `applyConfigOverlay` treats `model_selection` as canonical and propagates `provider_name` to the target's legacy field; `syncModelSelectionFromLegacy` mirrors legacy changes back into it. `parseObject` only populates `model_selection` when all required fields are present — since `api_key` is never serialized (lives in `auth.json`), disk-loaded configs **never** have `model_selection`. Callers that need `model_selection` after a fresh load must fall back to legacy fields (`config.provider`, `config.model`, `config.base_url`, `config.provider_name`), which ARE populated from `defaultModel` and `hydrateActiveModel`. **Zig footgun (crashed resume, fixed in 58a0537):** `Config.activeModelSelection()` and the owned `ModelSelection` accessors (`model()`, `providerName()`, `baseUrl()`, …) MUST take pointer captures (`|*ms|`, `|*b|`/`|*c|`) / a `*const ModelSelection` receiver. A *value* capture hands back `&b.model` / `b.provider_name` pointing into the method's popped stack frame — the caller's later reads (e.g. `reasoning.resolve()` after an intervening client-attach call) then hit "switch on corrupt value" on garbage. Method-call syntax auto-references values, so pointer receivers need no call-site changes; the returned pointers resolve into the caller's own storage.
- `tui.AtSearchState` — `union(enum) { closed, indexing, open }` with `IndexingPayload` and `OpenPayload` structs. `kind()`/`results()`/`close()` helpers bridge callers.
- `tui.NavState.quit` — `QuitState = union(enum) { none, pending, confirmed }` replacing `?Timestamp + bool`.
- `tui.NavState.session_action` — `SessionAction = union(enum) { browsing, renaming, deleting, blocked }`. Sub-states for the resume picker: `browsing` is normal navigation; `renaming` shows a text prompt; `deleting` shows Y/N confirmation; `blocked` shows a popup (e.g. "Cannot Delete Active Session"). Any key dismisses `blocked`; `renaming`/`deleting` submit on Enter and cancel on Esc.
- `tui.NavState.resume_group_by` — `ResumeGroupBy = enum { flat, project, date }` replacing `resume_global: bool`. Cycles via `Ctrl+A`: flat (current project only) → project (all projects, grouped by project) → date (all projects, grouped by date bucket: Today/Yesterday/This Week/This Month/This Year/Older). Tab only folds/unfolds in `.project` mode.
- `tui.ModelCatalogue.load` — `LoadState = union(enum) { idle, loading, failed }`.
- `search.Backend.state` — `State = union(enum) { idle, loading, ready, failed }`. The `.ready` arm owns a slab of null-terminated filepaths plus a count; matching is performed by the vendored `fzy` C library (`vendor/fzy/src/match.c`).
- `tui.MetricsState.diff` — `DiffState = union(enum) { idle, loading, ready, refreshing }`. The `refreshing` arm keeps the old cache while a new fetch is in flight. Backward-compat accessors (`diff_refresh_future`, `diff_refresh_done`, `diff_loading`, `diff_refresh_again`, `diff_cache`) preserve existing call sites after the flat-to-union migration.
- `config.ProviderModel = Model` — type alias removing duplicate struct drift.
- `config.BaseUrl` — `union(enum) { default, custom: []u8 }`. In overlay merges, `.default` means "don't override"; at final resolution it falls through to `Provider.defaultBaseUrl()`.
- `config.ReasoningSetting` — `union(enum) { unset, effort: ai.ReasoningEffort }`. Follows `BaseUrl`'s overlay-merge pattern: `.unset` means "not specified in this layer, don't override"; `.effort` carries an explicit level (including `.default` which omits the `reasoning_effort` request parameter). `resolve()` falls back to `.medium` for `.unset`.
- `session.SessionSummary.leaf_entry_id: ?EntryId` — branded `EntryId` (fixed-size `[entry_id_len]u8`) instead of loose `[]u8`.
- `model_loader.ModelSource` — `union(enum) { openai_codex, openai_compatible: Compatible }`. The `.openai_compatible` arm is a `Compatible` struct `{ provider, base_url, auth_key_id }` (all gpa-owned; `source.deinit(gpa)` frees the strings) rather than a bare `Provider` enum. A bare enum collapsed every dynamic/config provider (StepFun, Kimi, …) to `.openai_compatible`, so a multi-provider catalogue couldn't tell them apart and `applySelectedModel` connected to whichever URL was stashed in `cached_config`. Carrying the full connection per row makes the mismatch unrepresentable: `applySelectedModel` reads the selected entry's `conn` directly and never consults `cached_config.base_url`. The disk cache (`model_cache.Record`) serializes `authKeyId` (cache version 2; v1 is read back compatibly, resolving `auth_key_id` from the configured provider label).
- `tools.Schema.Property` — `nullable: bool` flag supporting OpenAI strict-mode union types (`["string","null"]`); `enum_values: ?[]const u8` for OpenAI enum schemas; `default_value: ?[]const u8` for JSON fragment defaults. The schema writer emits nullable union arrays only when `nullable` is set, while keeping nested object `additionalProperties: true` for free-form fields like `env`. Strict-mode emission (`"strict":true`, `additionalProperties:false`, and `required:[all properties]`) is gated by the `strict: bool` parameter (see the Tool schema strict-mode pattern below); when strict is off, `required` lists only genuinely-required properties and the `"strict"` key is omitted. `deinit(gpa)` frees owned `enum_values` and `default_value` slices.

### Models.dev provider filtering pattern

`parseModelsDevJson` in `src/models/registry.zig` includes any provider with a non-empty `api` field and ≥1 model — npm package identity is irrelevant. The `api` field is the ground-truth signal for Nova's `openai_compatible` adapter. `@ai-sdk/anthropic` providers with custom `api` endpoints (kimi-for-coding, minimax, etc.) are included; `@ai-sdk/openai` providers without `api` (openai, perplexity-agent) are excluded because `Provider.base_url` is non-optional. Providers without an `api` field (`@ai-sdk/google`, `@ai-sdk/azure`, etc.) are correctly excluded.

### Models.dev network-first loading pattern

`loadOrFetchRegistry` tries sources in order: (1) network fetch from `https://models.dev/api.json` with User-Agent `nova-agent/1.0`, (2) fresh cache (within 24h TTL), (3) stale cache (ignoring TTL), (4) vendored snapshot at `<exe_dir>/../share/nova/api.json` (installed by `zig build install`), (5) builtins-only fallback. The vendored snapshot seeds the cache directory (`~/.config/nova/cache/models.dev/api.json`) so subsequent starts skip the file read, ensuring 145+ dynamic providers are always available offline. `openProviderPicker` in `src/tui/provider_model.zig` deinits and reloads `provider_state.modelsdev_registry` every time the picker opens. Diagnostic logging at each stage (`modelsdev.fetch.ok`, `modelsdev.fetch.failed`, `modelsdev.cache.fresh`, `modelsdev.cache.stale`, `modelsdev.vendored`, `modelsdev.registry.fallback`) helps diagnose empty provider lists.

### HTTP fetch decompression pattern

`fetchApiJson` in `src/models/registry.zig` must honor `response.head.content_encoding`: gzip/deflate/zstd responses from Cloudflare-backed hosts (models.dev) are decompressed via `response.readerDecompressing` before caching; identity responses pass through unchanged. Using a plain `response.reader` stores compressed bytes in the cache, which `parseModelsDevJson` rejects, silently falling back to builtins-only (14 providers). `listModels` in `src/ai/openai_compatible_models.zig` already follows this pattern; `fetchApiJson` must match it.

### Dynamic provider connection pattern

When a models.dev dynamic provider is selected, `submitDynamicProviderSetup` stashes the provider's `base_url` and the user's API key into `cached_config` before entering the model picker, and stores two identity fields: `dynamic_provider_name` (human-readable, e.g. "StepFun AI", used by the status bar) and `dynamic_provider_id` (the auth.json key, e.g. "stepfun-ai"). Both are **runtime-only** — never serialized to config.json

**Selection-time resolution no longer reads `cached_config`:** `applySelectedModel` resolves the connection URL and key **directly from the selected entry's own `ModelSource`** — `ModelSource.openai_compatible` is a `Compatible` struct (`{ provider, base_url, auth_key_id }`), so each catalogue row carries its own full connection. `applySelectedModel` calls `compatibleApiKeyForConn(conn)` (auth.json lookup by `conn.auth_key_id`, fallback to anonymous/local) and `attachOpenAiCompatibleClient(conn.base_url, ...)`. The `cached_config.base_url`/`dynamic_provider_id` stash is now only for **session resume** (`tryAttachOpenAiCompatibleFromConfig`) and `hasOpenAICompatibleCredentials`; `updateCachedModelSelection` mirrors the entry's `conn` into the stash so resume stays consistent. This closed a class of multi-provider bugs where `cached_config.base_url` held a single global value and selecting a model from a different provider (in a `connected_provider` sweep) connected to the wrong endpoint or returned `NotConnected`. `compatibleBaseUrl`/`compatibleApiKey` (the provider-enum variants) are now test-only; do not reintroduce them on the selection path — use `compatibleApiKeyForConn` and the entry's `conn.base_url` instead.

### Dynamic provider persistence pattern

`serialize` writes `defaultModel: "provider_name/model_id"` as the single source of truth for provider identity — there is no separate `"provider"` field. `parseModelSelection` splits on the first `/` to recover `provider_name` and `model_id`. After restart, `model_selection` is usually null (because `api_key` is never serialized), so all rehydration paths fall back to legacy fields: `tryAttachOpenAiCompatibleFromConfig` resolves `base_url` from `config.base_url` (hydrated from the `providers[]` map by `hydrateActiveModel`), `model_id` from `config.model`, and the API key from `auth.json` via `config.provider_name`. `hydrateActiveModel` includes a recovery fallback: when `provider_name` is the generic enum label (`"openai_compatible"`) — e.g. from configs written before the `provider_name` serialization fix — it matches `.openai_compatible` entries in the `providers[]` map by enum and repairs `provider_name` to the actual id. `providerDisplayName` and `providerLabel` in `status.zig` fall back to `config.provider_name` / `config.provider` when `model_selection` is null. `buildMergedProviderList` Layer 3 skips config entries covered by the models.dev registry (`reg.lookup(cp.name)`) to prevent the persisted `ProviderConfig` from shadowing the `.dynamic` handle. `collectConfiguredProviders` block 3 uses a `covered_by_registry` guard (with `ms.provider_name` fallback for resume) and resolves the API key from `provider_state.api_keys` instead of the always-empty `ms.api_key`

**Disk cache (`collectModelCacheConfigured`) must mirror the online collector's two dynamic/config rules:** (a) every `.openai_compatible` entry in `cached_config.providers[]` with a custom `base_url` and a key in `auth.json` (config map key == `auth_key_id`), and (b) every models.dev dynamic provider present in `provider_state.api_keys` (key == registry id). The earlier code wrote only the single `model_selection` provider, so other connected dynamic providers vanished on restart. **Conn-keyed drops, never enum-keyed:** `dropConn` (catalogue) / `dropModelsForConn` (job) / `installModelLoadResult`'s merge `StringHashMap` are always keyed by `conn.auth_key_id` (or the full `(provider, base_url, auth_key_id)` triple), never by `conn.provider`. Enum-based `dropProvider` is correct **only for builtin catalogue providers** (each is its own enum value); on multi-`.openai_compatible` provider lists it collapses siblings and deletes unrelated providers in a single refresh. `openModelPicker` calls `ensureModelsDevRegistry` before `restoreModelCache` so the cache collector can see dynamic providers (the registry is otherwise loaded only by `openProviderPicker`). `startOpenAiCompatibleModelLoad` uses `.merge = true` (consistent with `startProviderModelLoad`) so adding dynamic/config providers preserves the existing catalogue and appends to it instead of wiping it via `codexModelsClear`.

### Mid-session model persistence pattern

The picker must mirror a model switch into the session DB, not only `config.json`. `applySelectedModel` resolves a `provider_name` (`Provider.openai.label()` for codex, `conn.auth_key_id` for compatible) and, after a successful client attach, calls `session_writer.updateModel(provider_name, model_id)` — the same call `runtime.applyFromConfig` makes. Without it the picker bypassed the session write, so `initResume` restored the stale creation-time model on restart. The write is **best-effort** (logged on error, never rolls back the applied client switch) and gated by `AgentRuntime.session_writer_started` (default `false`, set `true` in `initSession` after the writer thread is up). The gate exists because TUI test harnesses construct a partial runtime with `session_writer = undefined`; the flag lets them exercise the picker without touching sqlite. `hasOpenAICompatibleCredentials` was relaxed to match: since `api_key` never serializes, gating purely on the runtime stash made the disk-cache restore (`/models`) skip the dynamic provider on restart. The typed `model_selection` with a non-empty `baseUrl()` is now the durable signal (real key resolved from `auth.json` at fetch time); `shouldLoadConfiguredCompatibleCatalog` resolves `base_url` from `model_selection.baseUrl()` when the legacy stash is null. `model.id.len == 0` is guarded by `return error.EmptyModelId` before constructing the non-optional `ModelSelection.custom.model.id` — use a real early return, never `std.debug.assert`, because `unreachable` is UB in ReleaseFast (the install target) and would not protect that build.

### Typed callback pattern

`agent.Listener(Ctx)` and `executor.ToolCallObserver(Ctx)` are generic over the consumer's context type. The `*anyopaque` + `@ptrCast` vtable is replaced by `*Ctx` + typed callback functions. `StreamContext(L)` and `ExecutorBridge(L)` are generic over the listener type. The sole remaining `@ptrCast` is `BashApproval` (1 site, deferred because making it generic would require `Agent` itself to be generic).

### Manual compaction trigger pattern

`Agent.forceCompact()` is a synchronous public method that runs the full compaction cycle (snapshot → summarize → swap) and returns `!Event.HistoryCompacted` with token counts before/after. Unlike the automatic path (which runs between turns inside `agent.run()`), this is callable from the TUI command handler. The caller is responsible for turn-safety: check `app.thread.turn.isActive()` before calling. Errors are surfaced to the user via transcript notices rather than swallowed in logs.

### Config layering pattern

Nova merges global (`~/.config/nova/config.json`), project (`.nova/config.json`), and env-var overlays into `cached_config`.

**Schema v2:** JSON keys are camelCase (`defaultModel`, `baseURL`, `mcpServers`, `useResponsesEndpoint`, `strictOutputs`, `systemPrompt`, `bashClassifierUrl`); legacy snake_case keys are parsed for backward compatibility but are **not schema-valid** — `schema/config.schema.json` uses `additionalProperties: false`, so a strict validator rejects them even though Nova's parser accepts them and rewrites them as camelCase on the next save. The legacy `enableThinking`/`enable_thinking` key is accepted-but-discarded (reasoning is per-model via `providers.<name>.models.<id>.reasoningEffort` — see **Reasoning effort lifecycle pattern**). `defaultModel`'s pattern `^[a-zA-Z0-9._:+-]+/.+$` allows `:` and `+` in both halves (model ids like `gemma4:31b`; provider ids with those chars). `version` is a semver string (`"2.0.0"`); legacy integer `1` normalizes to `"1.0.0"`. `applyConfigOverlay` uses an if/else structure: `model_selection` is canonical; legacy fields are fallback. `syncModelSelectionFromLegacy` mirrors legacy changes back into `target.model_selection` via `|*ms|` pointer capture. `serialize` skips `api_key` (lives in `auth.json`) and writes camelCase keys. `saveSettings` writes only settings-managed fields — never provider/model. At connection time, `tryAttachOpenAiCompatibleFromConfig` and `tryAttachOpenAiResponsesFromConfig` resolve an empty `ms.base_url` through `provider.defaultBaseUrl()` so client `init` never sees an empty URL.

### Reasoning effort lifecycle pattern

Reasoning is controlled per-model and flows through a single chain: model picker (`Model.reasoning_options` from config `reasoningOptions`, cached in `app.provider_state.reasoning_opts_cache`; empty = global hardcoded list) → `selectedReasoningEffort()` → `attachOpenAiCompatibleClient(effort)` / `persistModelSelection` → wire. The wire field is dialect-gated (`ai.WireDialect`, Phase 1): DashScope uses top-level `enable_thinking`, OpenRouter uses a `reasoning` object (`{"effort":"...","summary":"..."}`), every other provider gets flat `reasoning_effort` (`.none` → `"none"` or `enable_thinking:false`). Effort levels: `default/minimal/low/none/medium/high/xhigh/max` (`max` is OpenRouter-specific, highest above xhigh). The session DB stores the active effort label in `sessions.reasoning_effort` (schema v5, nullable; NULL = "use config/default"). `Session.updateModel(provider, model_id, effort_label)` writes it from `applyFromConfig` (resolves `model().reasoning.resolve().label()`) and `applySelectedModel`; `initResume` restores it via `ai.ReasoningEffort.fromString` (invalid DB labels degrade to "no override", never fatal). The status bar shows the live effort (`src/tui/status.zig`, `ModelStatus.reasoning`, source priority: live client config → model selection → "medium") as `provider · model [effort]`. The model picker no longer has a SCOPE column — the save scope (global/project/session) is cycled with **Ctrl+S** inside the picker and displayed in the footer status line next to a wire-parameter preview (`→ reasoning_effort:"high" (Ollama)`, `enable_thinking` for DashScope).

**Ollama Cloud / local Ollama `reasoning_effort` clipping (added 2026-08-09).** Both Ollama Cloud (`https://ollama.com/v1`) and local Ollama (`http://localhost:11434/v1`) use the **OpenAI-compatible `/v1/chat/completions`** endpoint — NOT the native `/api/chat` format. The native `/api/chat` fields (`think`, `format`, `options`, `keep_alive`) are absent on `/v1`. Ollama's `openai.go` validates `reasoning_effort` **strictly**: only `high`/`medium`/`low`/`max`/`none` are accepted — sending `xhigh` or `minimal` returns HTTP 400 (`"invalid reasoning value: '...' (must be \"high\", \"medium\", \"low\", \"max\", or \"none\")"`). Both invalid values are reachable on Ollama Cloud because the builtin registry entry declares no per-model `reasoning_options`, so the global hardcoded list (which includes `xhigh` and `minimal`) is offered. `wireEffortLabel` (`openai_compatible.zig`) clips them for the `.minimal` dialect only — `xhigh → "max"`, `minimal → "low"` — while the `.openai` dialect keeps the raw label (gpt-5 honours both). The stream parser recognises `delta.reasoning` as the reasoning field (Ollama's `/v1` response; DeepSeek/others use `reasoning_content`, and `thinking` is recognised as a fallback for OpenAI-compatible proxies that forward Ollama's native field name). Tool calls come back in the standard OpenAI shape (`message.tool_calls[].id/function.name/function.arguments`); `tool_choice:"auto"` is silently dropped by Ollama (unsupported) but harmless to send.

### Context & compaction config pattern

`Config.context: ContextSettings` carries `overrideContextWindow`, `maxOutputTokens`, `disablePromptCache`, and `compaction: CompactionSettings` (auto, threshold, keepRecentTokens — the old `bufferTokens` was removed, it never did anything). The runtime stores `context_settings` and passes `override_context_window` to `compaction.contextWindowTokens()` at client attach time. The agent stores `compaction_settings` and passes `threshold` to `shouldStartSummary`/`shouldSwap` and `keep_recent_tokens` to `keepRecentTokens`. When `auto` is false, `maybeCompact` returns immediately. The swap watermark is `threshold + 0.20` (capped at 0.95); `threshold` is clamped at parse time to [0.1, 0.90] so the swap watermark can never fall below the start watermark. `startCompaction` calibrates the keep-recent budget by the ratio of the provider's real token count to the chars/4 estimate (`calibrateKeepBudget`) so CJK text keeps fewer messages and still compacts below swap. Background-summarizer clients (codex / openai_responses) receive the minimal `compaction.summarizer_system_prompt` — never the full agent system prompt — so the summary request itself fits a small window. The automatic path carries a circuit breaker: after 3 consecutive failures it backs off (one transcript notice, `compaction_notice` event) and only `/compact` remains. `forceCompact` drains any in-flight background summary before starting (TD-1), as does `navigateToEntry` before a branch switch (TD-2). JSON Schema for editor autocompletion lives at `schema/config.schema.json`.

**Codex Responses encrypted-reasoning replay:** `ResponsesConfig.include_encrypted_reasoning` and `scrub_encrypted_reasoning` are internal transport settings, not user configuration fields; do not add them to `schema/config.schema.json` or `docs/CONFIG.md`. The standard Responses client keeps encrypted reasoning enabled and preserves persisted `responses_item_json`. The ChatGPT Codex transport disables the server include and enables replay scrubbing because the Codex backend rejects persisted `encrypted_content` with a misleading 400. The scrubber removes only the top-level `encrypted_content` field, skips malformed/non-object JSON without failing the request, and is covered by tests for both Codex cleanup and standard Responses preservation. Keep these controls separate: requesting encrypted reasoning and sanitizing replayed history are different concerns.

**`disablePromptCache` (C1, added 2026-08-06):** a user-facing escape hatch for OpenRouter `:free` / gateway-fronted models (kimi, inclusionai/ling) that reject `cache_control` and/or `session_id`/`prompt_cache_key` with HTTP 400. When true, the flag suppresses ALL cache fields in BOTH wire clients — OpenRouter top-level `cache_control` + native `session_id`, OpenAI `prompt_cache_key` (chat-completions AND Responses-API `responses_core.writeRequestPayload`, the latter being ungated by dialect today) — regardless of the resolved `WireDialect`. It flows `context.disablePromptCache` → `AgentRuntime.disable_prompt_cache` (set at the dialect-resolution site in `tryAttachOpenAiCompatibleFromConfig`, read from `context_settings` for ALL client kinds) → `ai.Config.disable_prompt_cache` on every attached client (main/compaction/naming for all three client kinds). It is also the durable complement to the automatic C2 downgrade retry (`errorDetailMentionsCache`) — set it once for a known-bad model and never see the 400.

**`toolCallLimitPerTurn` / `softStopOnToolCallLimit` (added 2026-08-22):** the per-turn tool-call budget that bounds `Agent.run`'s iteration loop. Both keys live under `context.*` and parse in both camelCase and snake_case (`u32fieldCompat`/`boolFieldCompat`, camelCase wins; 1–1000, out-of-range dropped). They resolve onto plain `Agent` fields in `initSession` right after the `compaction_settings` copy — following that pattern, NOT the client-attach resolution — so test-built agents keep working off field defaults and every runtime flavor (primary, `/new`, `/resume`, lane workers) inherits them. On exhaustion with soft-stop enabled, `softStopOnBudget` drains the whole queued-message backlog into history (`drainAllQueuedToHistory` + `queued_messages_flushed`), appends a static `[nova]` continuation hint, and emits the allocation-free `tool_budget_exhausted: u32` event before returning normally — the run always terminates, continuation is the user's next submit (TD-6: no auto-resume). The hint is a `.user` machine message, deliberately NOT `.system`: `SessionWriter.append` skips `.system` (writer.zig), so only `.user` survives `/resume`, branch switches, and compaction reprojection — and Qwen's single-leading-system normalization never touches it. With `softStopOnToolCallLimit: false` the loop keeps the historical `error.ToolCallLimit` contract byte-for-byte.

### Toast notification pattern

Design spec: `_plan/plan-toast-system-2026-08-07.md`. A generic, thread-safe toast bus any subsystem can push to — **not** logger-specific (future pushers: MCP connect/disconnect, lane spawn/merge, background jobs, permission denials). Two decoupled pieces: `ToastBus` (`src/tui/toast.zig`) — a global ring buffer (`global`, a singleton because the logger is itself a global cross-thread struct); and `Widget` — a passive top-right overlay (no focus, no key capture). Key files: `src/tui/toast.zig` (`push` cross-thread entry, `drain` UI-thread entry), `lib/logger.zig` (`Options.toast_sink: ?*const fn (std.log.Level, []const u8) void` opaque callback — logger stays TUI-agnostic, no `lib → src` dependency), `src/root.zig` (`toastSink` adapter maps `std.log.Level`→`toast.Level`; `resolveStderrLevel` returns `?Level` so `stderr_explicit` distinguishes env-set from default), `src/tui/lifecycle.zig` (`handleTick` drains the bus; `should_tick` keeps polling while `toast.global.hasToasts()`), `src/tui/root_layout.zig` (toast child at `z_index = 4`, above all others)

**Routing in `logger.dispatch`:** warn+ goes to the toast sink when one is installed AND `stderr_explicit` is false (the TUI-tearing fix — stderr bytes land in the alternate screen and tear the frame); when `NOVA_LOG_STDERR_LEVEL` is set, warn+ goes to BOTH stderr and the toast; with no sink (headless/tests) stderr keeps the default gate. **Push-path discipline:** `push` allocates NOTHING — `Item.msg` is a fixed 1024B inline buffer (`@memcpy` truncates), so worker threads never touch the heap here. Locking is `std.Io.Mutex` (NEVER `std.atomic.Mutex` — that's a spinlock, see AGENTS.md §Gotchas); `push`/`drain`/`dismiss` all `lock(io) catch return` (a failed lock drops the toast, never panics). `hasToasts()` is a deliberate lock-free `count > 0` read used only as a visibility hint — a stale value at most delays/advances one frame. **`drain` is called twice per visible frame** (once in `handleTick`, once in `Widget.draw`) — both take the lock; the second is effectively a no-op if the first cleared the ring, which is the intended cadence. **Config:** the `toast` section mirrors `context` (`parseToast`/`writeToast`/`hasNonDefaultToast`/`applyToastOverlay`) — all fields optional, section omitted from config.json at defaults. Out-of-range `durationMs`/`maxVisible` are **dropped** (left null) at parse, NOT clamped — distinct from the `threshold` clamp in the compaction pattern; a typo can't produce a toast that never dismisses or a stack covering the screen. Only `enabled` is surfaced in the `/settings` General tab (applied live); `durationMs`/`maxVisible`/`position` are config-file-only. `position` is reserved (only `top-right` rendered today). **`initialized` guard:** `ToastBus.init` sets `initialized = true`; `push`/`drain`/`hasToasts` early-return when false, so calls before `tui.run` inits the global (e.g. a test driving `handleTick`) are safe no-ops rather than touching an uninitialized `io`/mutex.

### Cross-project session resume pattern

The session DB is global (`~/.config/nova/sessions.sqlite`), so the `/resume` picker's `project` and `date` group-by modes list sessions from all projects. When a user resumes a session whose `cwd` differs from the current runtime's cwd, `createRuntime` (session_switcher.zig) detects the cross-project case (`session_id != null and cwd != current.cwd`) and does three things: (1) sets `template = null` so `initSession` loads skills and plugin prompts from the session's own cwd instead of cloning the current runtime's; (2) calls `config_mod.load` with the target cwd to reload `.nova/config.json` so MCP servers, model selection, and project-scoped settings match the session's project — the env layer is constant (process env vars don't change between projects), so the `environ_map` captured at startup (`App.environ_map`, threaded through `initRuntime`) is reused; (3) after `initResume`/`initNew` succeeds, replaces `app.cached_config` with the reloaded config and calls `mcp_manager.syncFromConfig` to reconcile MCP clients. If config reload fails, the current config is used as fallback (logged, never fatal). `switchToSession` receives `summary.cwd` from the caller (`mode_lifecycle.submitMode`) and passes it to `createRuntime` instead of the current runtime's cwd

**`cwd` ownership:** `initSession` dups `cwd` into runtime-owned memory (freed in `AgentRuntime.deinit`), so the borrowed `summary.cwd` can be freed by the next `reloadResumeSessions`→`resumeClear` without dangling the runtime's workspace path. Without the dupe this was a use-after-free: `repoRoot()`/`liveRuntime().?.cwd` returned the freed pointer and `manager.list`→`bindText(1, cwd)` read it — deterministic once `db.zig` bound with `sqlite_transient` (copies at bind) instead of the old `sqlite_static` (kept the pointer, deferred the read to step). `home_dir` stays borrowed (root-owned, never freed, valid for the app lifetime).

### Text-emitted tool calls recovered pre-persist (T1/T2/T3)

Some function-calling models (ling-3.0-flash, weaker gateways) emit valid tool *intent* as literal text inside a `{"type":"text"}` block (`<tool_call>bash<arg_key="command">…</arg_key></tool_call>` or `<tool_call>{"name":…,"arguments":{…}}</tool_call>`) instead of structured `tool_calls` deltas. The stream parser only reconstructs structured deltas, so such a turn has zero `.tool_call` blocks and the agent goes idle as if the model said nothing. Recovery (`recoverTextToolCalls` / `injectRecoveredToolCalls` in `src/agent.zig`, parser in `src/ai/text_tool_call.zig`) runs in the narrow window BETWEEN `collectToolCalls` and `takeAssistantMessage` in the turn loop (agent.zig `runPromptedTurn`) — it MUST run there because `takeAssistantMessage` invalidates `turn.assistant` (`= undefined`), and `hasWireContent` is `true` for a text-only message, so by the `len == 0` site the message is already gone. Ownership: `recoverTextToolCalls` returns freshly-allocated `ToolCall`s (their `call_id`/`name`/`arguments` are minted in the parser), `injectRecoveredToolCalls` appends them as new `.tool_call` ContentBlocks reallocating the content slice, and the SAME `recovered` slice drives execution (no re-collect). This mirrors `collectToolCalls`'s aliasing contract (slice shell caller-freed; element strings belong to the message). Conservatism guards: only fires when structured calls are zero, only scans `.text` blocks, and the parser only matches the explicit `<tool_call>` envelope — free-form angle brackets are never misread. The system prompt (`<tool_calling>` block) also directs compliant models never to emit tool calls as text (T2), so this is a safety net for models that ignore the directive.

### LLM request diagnostics carry model identity (L1/L2/L3)

`logBytes` (`openai_compatible.zig`) used to truncate at 12KB head-only; because JSON key order is `model → messages → … → tools`, a realistic system prompt + a few turns already consumed the head, hiding the `tools` array (the most-wanted field when debugging tool-calling). It now appends a tail slice starting at `"tools":` when truncating, so the array is visible without reverse-engineering the payload from test fixtures. Callers must `defer`-free only when `result.ptr != bytes.ptr` (short bodies alias through). Separately, the `tools_json == "[]"` warning is emitted from `Client.prompt` (not the free `writeRequestPayload`) so it carries `self.url` + `self.config.model`, disambiguating the tool-less summarizer/naming clients from a tools-less main client.

### Streaming tool-call cap pattern

Chat-completions `stream_parser.zig` carries a **hard** cap (`tool_call_array_cap = 64`) and a **configurable** cap (`max_calls`, default 16). The hard cap protects fixed `remapped_slot[64]`/`is_remapped[64]` arrays and still aborts with `error.TooManyToolCalls`. The configurable cap is a *drop* gate: deltas whose logical index is ≥ `max_calls` are parsed to completion (so later argument chunks for the same dropped call do not corrupt the SSE stream), counted in `ToolCallStream.dropped`, and skipped without touching `builders` or observer callbacks. The turn therefore completes with the first `max_calls` calls instead of failing entirely. The final `readStream` log line (`readStream.dropped`) surfaces the count. The Responses-API client's separate local `readStream` has no `max_calls` path, so this cap/drop logic applies only to the chat-completions client today.



### Lane workspace boundary

The model-facing `lane` tool is orchestration-only: the primary driver
supervises workers with `spawn`, `read`, `await`, `steer`, `cancel`, `merge`,
and `delete`. Internal workspace state (`Agent.workspace` and executor
`effectiveCwd` re-rooting) remains for lifecycle compatibility and tests, but
is not reachable through the model parser. This prevents driver tool calls from
running in a worker worktree while preserving the existing cleanup path.

`/parallel` creates a live user-selected lane. `drawLaneColumn`
(`src/tui/lane_column.zig`) renders activity from that lane's own turn state,
so prompts submitted in `grid` or `tab` run in the selected lane's worktree.
`dual` keeps the primary as the input target. After the lane is idle and clean,
the user can open `/merge` directly from the selected lane, or the primary
driver can merge/delete it by lane id. See issue #23 for the original activity
visibility analysis.

### Windows portability pattern

The app compiles on Windows (Zig 0.16) without breaking Linux. `lib/platform.zig` centralizes the OS-adaptive helpers so the rest of the codebase stays clean of `builtin.os.tag` switches:

- Use `platform.getEnvMap` instead of raw `std.c.environ` reads.
- Use `platform.writeToFd` instead of `std.c.write`.
- Use `platform.realtimeNowNs` / `platform.monotonicNowNs` instead of `std.c.clock_gettime`.

Guard POSIX-only syscalls behind `if (!os.is_windows)` at their call sites: `std.posix.kill`, `std.posix.poll`, `setsockopt`, `std.c.realpath`.

**`zeroedChild()` helper (`src/mcp/client.zig`):** `std.mem.zeroes(std.process.Child)` is a compile error on Windows because `Child.thread_handle` is a non-nullable `HANDLE`. Use the `zeroedChild()` helper to construct a zeroed `Child` portably instead of calling `std.mem.zeroes` directly.

Note: this covers **compilation** only. Full runtime support on Windows is still in progress — see the follow-up issues (#26 config paths, #27 bash shell, #28 failing tests, #29 lanes).

### Worktree Hardening & Lifecycle Architecture

Worktrees isolate parallel worker agents and user lanes from the primary repository tree. Five architectural pillars ensure robust, cross-platform stability:

1. **Path Normalization (`src/paths.zig::pathsEqual`):**
   Path equality checks for workspace borrows, worktree directories, and lane commands use `pathsEqual` from the root leaf `src/paths.zig` (re-exported as `lanes_util.pathsEqual` by `src/tui/lanes.zig` for in-TUI callers; the execution layer imports the leaf directly). This helper operates with zero dynamic allocations, collapses redundant and trailing slashes (`/` vs `\`), and applies ASCII case-folding on Windows (`C:\foo` == `c:/foo/`). Never compare file or worktree paths with byte-level `std.mem.eql`.

2. **Shell Containment Parity:**
   Worker agents are strictly root-contained. On POSIX, `bash.zig` validates directory navigation. On Windows, `src/tools/pwsh.zig` injects pre-command function overrides (`cd`, `Set-Location`, `chdir`, `sl`) that resolve target paths with `[System.IO.Path]::GetFullPath`, check boundaries with `$root.TrimEnd('\', '/')`, and reject directory-stack escapes (`Push-Location`, `Pop-Location`).

3. **Windows File Locking & Teardown Protocol:**
   Deleting worktrees on Windows is subject to asynchronous file lock retention by child processes or Windows Defender. All teardown paths (`abandonLane`, `mergeLane`, `deleteSelectedParked`, `rollbackLaneWorktree`, `deleteLaneOp`) call `lane_lifecycle.cleanupLaneWorktreeAndBranch`:
   - Synchronously terminates all child background processes running in or below the worktree (`background.terminateJobsInCwd` via `terminateTreeSync`).
   - Executes `vcs.worktreeRemove` with a 4-attempt retry loop and exponential backoff (50ms, 150ms, 300ms).
   - Runs `vcs.worktreePrune` (`git worktree prune --expire now`) to purge administrative metadata in `.git/worktrees`.

4. **Startup Orphan Garbage Collection:**
   Global worktree checkouts reside at `<home>/.config/nova/worktrees/<id>` (resolved portably via `vcs.globalWorktreesDir`). During startup hygiene in `src/root.zig:run()`, `vcs.gcOrphanedWorktrees` scans this directory and removes abandoned checkouts older than 7 days (`vcs.worktree_retention_ns = 7d`). When launched in a Git repository, `vcs.worktreePrune` synchronizes `.git/worktrees` metadata before any session or lane initializes.

5. **Asynchronous Non-Blocking Worktree Provisioning:**
   In large repositories, `git worktree add` can block the host process for 2–5 seconds. `spawnLane` offloads worktree creation to a background worker thread (`WorktreeJob`) and returns `null` on the first tick, keeping the request queued in `LaneBridge.pending`. The TUI event loop continues ticking at 30ms, while `advanceAnimations` and `decideShouldTick` query `lane_lifecycle.anyAsyncWorktreeActive` to drive loading spinners smoothly until provisioning completes.

### Plugin Discovery Lifecycle

Project-scoped Lua plugins (`.nova/plugins/*`) are discovered **once** at App startup via `PluginManager.init` → `syncPluginConfig` → `loadAll`. The loaded set is immutable mid-session to avoid two free hazards:

- **Lua state frees:** unloading a plugin calls `PluginInstance.deinit`, which destroys its sandboxed Lua state. Any lane worker mid-dispatch through a plugin handler would be killed.
- **Registry tool-record frees:** `registerPluginTools` (`src/tui/provider_model.zig`) strips all `lua__`-prefixed tools from the shared `ToolRegistry` before re-adding. A worker dispatching through a tool record that `removePluginToolsWithPrefix` just freed is a use-after-free.

There is exactly **one** mid-session exception: a guarded cross-project `/resume`. When `createRuntime` detects `cross_project` (session cwd differs from the current runtime's cwd), it runs:

1. `anyLaneTurnActive` guard — iterates every lane; if any has a turn in `.active` or `.interrupting` state, the switch is refused with `error.InFlightTurn`. The guard runs synchronously on the UI thread with zero yield points, so no idle→active transition can interleave.
2. `syncPluginConfig` — applies the reloaded project's enable/disable + settings (build-then-swap: error leaves the previous set intact).
3. `repointProjectDir` — unloads old project plugins by directory prefix (with separator-boundary check), frees the old `project_dir`, loads from the new project's `.nova/plugins/`. Re-scans the global dir for plugins that were shadowed by the old project and are now absent.
4. `registerPluginTools` — strips the previous `lua__` generation and re-adds from the live manager (idempotent; descriptor-build failure leaves the stale-but-valid set).

Global plugins (loaded from `~/.config/nova/plugins/` or `%APPDATA%/nova/plugins/`) are never touched during a repoint — their Lua states, event subscriptions, and `require` caches survive the switch. New-project plugins that share a name with a global override the global (mirroring `loadAll` semantics).

Known limitation: live lane clients keep their spawn-time `tools_json` until their client is rebuilt, matching the existing MCP-config change behavior on session switch.
